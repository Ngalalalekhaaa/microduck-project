# HD-1910 / Radxa Zero 3W 部署评估

核查日期：2026-09-27。依据本地源码、飞特运行时分支及用户提供的硬件信息；尚无这台机器的传感器日志或台架测量。

**2026-09-28 更新：**用户已授权接续训练。独立工作树
[`microduck_rl_hd1910`](../microduck_rl_hd1910/docs/hd1910-training.md) 已补齐 HD-1910 平地和齿隙任务，
并通过 CPU 配置与执行器测试；GPU 验证及短训练排在原版两版完成之后。
下文“缺少齿隙实现”描述的是最初克隆的上游版本。直连 IMU、飞特运行时和实机标定缺口仍需处理。

## 结论

**当前训练的 XL330 策略不能视为可直接在这台 HD-1910 Microduck 上行走的成品。** ONNX 接口可以复用，但需要在 HD-1910 动力学下重新训练或微调，同时补全飞特舵机与直连 IMU 的运行时接入。仅修改串口、模型路径或电压配置无法完成适配。

现有检查点可保留作对照和暖启动候选；暖启动也需要继续训练和评估，不保证比从头训练更好。

## 已确认的硬件

| 部件 | 用户提供的信息 | 对训练/部署的影响 |
|---|---|---|
| 舵机 | 飞特 HD-1910 | 改执行器动力学、飞特通信、逐关节标定与增益 |
| 主控 | Radxa Zero 3W | 官方运行时已有 ARM64/Radxa 构建与部署支持 |
| HAT | 电池接 HAT，HAT 降压 5V 给 Radxa | 核对 UART 和实际供电；5V 是主控电压，不能填入舵机模型 |
| IMU | LSM6DSV16XTR，直接连接 Radxa | 新增 Linux 直连读取路径；不使用 STM32/总线 ID 200 路径 |
| 电池 | 用户称 7.4V 电池 | 训练需要覆盖舵机端实际充电状态和负载压降，不能按恒定 7.4V 处理 |

尚需确定 IMU 使用 I²C 还是 SPI、具体引脚/设备节点、安装方向及 Radxa 系统镜像。接口不同会改变驱动和设备树，但不改变以上结论。

## 一、为什么需要 HD-1910 训练

当前正式任务是 `Mjlab-Velocity-Flat-MicroDuck` 和排队的 `Mjlab-Velocity-Flat-Backlash-MicroDuck`。两者都使用官方 XL330 BAM M6 参数；齿隙版仍是 XL330，只额外模拟机械间隙。

证据：[官方执行器配置](../microduck_rl/src/mjlab_microduck/robot/microduck_constants.py) 使用 `motor_name="xl330"`、`kp_fw=200`、`vin_range=(6.5, 8.2)`。电压范围覆盖 7.4V 不代表电机、摩擦和固件控制规律匹配。

复刻仓库已有 [HD-1910 平地任务工厂](../microduck-replica/software/training/src/mjlab_microduck/tasks/microduck_hd1910_env_cfg.py)：

- `Mjlab-Velocity-Flat-MicroDuck-HD1910` 加载公开的 `1910_m6.json`。
- 基线为 `kp_fw=5`、`vin_range=(7.4, 8.0)`、`vin_min=7.0`；这些是上游设置，尚未按用户机器测量。
- [飞特执行器适配](../microduck-replica/software/training/src/mjlab_microduck/actuator/feetech_bam.py) 修复控制器目标历史的初始化与 reset。
- 几何、质量和惯量仍沿用官方机器人，需要核对实际 HD-1910、HAT、电池及安装件造成的质量与重心差异。
- 参数来自 LuwuDynamics 的公开辨识结果，不是这台机器人实测；[参数来源和已知限制](../microduck-replica/software/training/src/mjlab_microduck/robot/hd1910/README.md) 记录了训练 P=5 与另一份 Arduino 运行配置 P=6/D=20 的差异。

### 齿轮误差版还需要补实现

目前没有注册 HD-1910 + Backlash 任务。[`make_backlash_variant()`](../microduck-replica/software/training/src/mjlab_microduck/tasks/backlash.py) 会替换整个机器人配置，直接套用它可能把执行器换回 XL330。

应组合：平地齿隙几何、HD-1910 参数、飞特目标历史 reset、`q_main + q_backlash` 编码器反馈及正确的主动关节筛选。按实测设置齿隙幅度；现有 ±1°（总 2°）只是训练假设。机械齿隙也不能代替固定零位偏差、控制延迟或摩擦误差。

### 复用当前权重时的注意点

当前官方 [tasks/mdp.py](../microduck_rl/src/mjlab_microduck/tasks/mdp.py) 支持 `MICRODUCK_WARM_START=1`，加载权重、归一化及优化器后重置课程/迭代计数。复刻训练目录对应文件没有这项补丁，不能只复制环境变量并认为已经完成暖启动。

应在同一训练代码版本下接入 HD-1910 两个任务，核对观测顺序、初始站姿、动作比例和归一化，再决定从头训练或暖启动。先进行短训练和配置检查，再启动正式训练。

## 二、部署代码需要改哪里

### 1. 飞特舵机后端

本地官方 `microduck` 为 `a9ec4b2`（0.15.0），尚无飞特后端。可参考 [fanhao375/microduck 的 feetech 分支](https://github.com/fanhao375/microduck/tree/8db8f00c8fc5278d0bdf43f96934531c37ee2780)，它基于 0.14.1，不能直接用旧版 main.rs 覆盖新版。

需要移植/调整的文件：

| 文件 | 修改内容 |
|---|---|
| `duck-control/src/bus_feetech.rs`（新增/移植） | 飞特 v1 协议、位置/速度/电流换算、P/D/I 和模式检查；接入真实传感器结果 |
| `duck-control/src/bus_select.rs`、`lib.rs` | 选择并导出飞特后端 |
| `robotd-params/src/lib.rs` | 登记总线类型、飞特参数和直连 IMU 配置 |
| `robotd/src/main.rs` | 构造实际使用的舵机和 IMU 后端 |
| `deploy/robotd.toml` | 选择飞特、正确 UART、逐关节方向和策略配置 |

官方当前版本还没有 `bus.protocol` 参数；只在官方配置里加入 `protocol="feetech-sts"` 不会得到飞特支持。新版 Dynamixel 的 `fast_sync_read` 使用协议 2 指令，不能套到飞特协议 1。

远程飞特后端仍有需要校正的假设：

- 位置默认以 raw 2048 为零，没有逐关节零位偏移配置。需机械/寄存器校零，或增加明确的偏移表。
- 速度单位目前只读取第一颗舵机的 phase，随后用于全部舵机；应逐颗确认或分别换算。
- `p_scale=0.16` 只是寄存器数值映射，默认运行增益 200 会得到 P=32，不能当作训练 P=5 的等效值。应根据 HD-1910 的实际控制模式、P/D/I 和响应统一训练与运行参数。
- 关节方向必须逐颗标定，不能照搬其他装机的全 `1` 或全 `-1`。

### 2. Radxa 直连 LSM6DSV16XTR

目前官方 [imu.rs](../microduck/duck-control/src/imu.rs) 解码的是 STM32 IMU 小板通过舵机总线提供的数据。远程飞特分支 `bus_feetech.rs` 填入 `ImuData::default()`，`imu_ready()` 恒为 false；不能直接用于用户的直连方案。

建议新增 `duck-control/src/imu_lsm6dsv16x.rs`（建议文件名，当前不存在），读取 I²C/SPI 或系统 IIO 数据，再组合到 [`RobotIo::read()` 返回的 Sensors](../microduck/duck-control/src/io.rs)。舵机数据来自 HAT 串口，IMU 数据来自 Radxa 的独立接口。

可新增 `imu_source.rs` 保存带单调时间戳及有效性标志的最新样本，由独立线程读取传感器，`FeetechIo` 只取非阻塞快照。这能保留现有控制和安全接口，并避免传感器读取阻塞控制循环。新增模块还需在 `lib.rs`、`Cargo.toml` 和运行时构造代码中接入。

接入要求：

- 初始化量程、采样率及 FIFO；优先复用芯片 SFLP 姿态融合能力，取得陀螺仪和姿态/重力信息。
- 如果使用内核 IIO，要确认板上内核及驱动实际提供所需通道；支持原始加速度/陀螺仪不自动代表提供 SFLP 四元数。
- 陀螺仪输出为机身坐标系 rad/s，重力为单位向量，直立约 `[0, 0, -1]`，四元数约定为 `[w,x,y,z]`。
- 按实际安装方向设置 sensor→trunk 旋转。现有默认转换 `[raw_z, raw_y, -raw_x]` 仅对应原版安装；不能直接假定适用。
- 用采样时间戳/计数判断新鲜度，处理初始化、断线、超时及恢复。仅在有效姿态数据到达后报告 ready，失效后撤销 ready。
- 不可将 `imu_ready()` 强行改成 true，或用固定重力向量代替真实数据。
- 直接解析 FIFO 时，有效 SFLP 样本的 XYZ 全零可以表示单位四元数；不能照搬现有总线解码器把全零当作未就绪占位的约定。
- 50Hz 控制循环每轮预算 20ms，应实测串口读写、IMU、推理和调度的总延迟。

ST 提供 [LSM6DSV16X 官方驱动](https://github.com/STMicroelectronics/lsm6dsv16x-pid) 及 [SFLP 示例](https://github.com/STMicroelectronics/STMems_Standard_C_drivers/blob/master/lsm6dsv16x_STdC/examples/lsm6dsv16x_sensor_fusion.c)。直接连接 Radxa 不要求换 IMU，也不要求为了板卡型号改变策略网络。

Rust 运行时也可使用 [ST 官方 Rust 驱动](https://github.com/STMicroelectronics/lsm6dsv16x-rs) 配合 Linux 总线适配。已核查该驱动有 I²C/SPI、SFLP 启用及 FIFO 接口；示例的采样率和量程不能直接照抄，应与运行时换算一致。可从现有项目的 120Hz、±500dps 基线开始验证，再根据实测调整。

### 3. 模型、动作与电压

- [`obs.rs`](../microduck/duck-control/src/obs.rs)：保持训练相同的 61 维观测顺序、单位和意义。
- [`model.rs`](../microduck/duck-control/src/model.rs)：核对 ID、关节顺序、限位和默认站姿；15 颗舵机中的嘴部不属于策略的 14 维动作。
- `robotd/src/control.rs`：`target = DEFAULT_POSITION + action_scale × action`，站姿与比例应和所导出的行走任务一致。
- 导出包含训练归一化的 ONNX，使用同一组输入核对 Python 和 ARM64 运行时输出。
- `deploy/robotd.toml` 中的 `nominal_voltage=7.4` 不会把 XL330 策略变成 HD-1910 策略。现有 `voltage_adapt` 动作补偿应在 HD-1910 基线中明确设定；可先关闭，以免引入未验证的动作缩放，再按实测评估。
- 训练电压以 HAT 后舵机实际端电压为依据，覆盖使用中的电池范围和负载压降。Radxa 的 5V 降压输出不是舵机模型的输入电压。

### 4. Radxa 启动配置

官方 [.cargo/config.toml](../microduck/.cargo/config.toml) 和 [setup-board.sh](../microduck/scripts/setup-board.sh) 已支持 Radxa/ARM64，默认舵机串口 `/dev/ttyS2`、`uart2-m0`。具体节点仍需按实际镜像与接线确认。

复刻仓库的 [做卡工具](../microduck-replica/tools/radxa/README.md) 使用 `/boot/extlinux/extlinux.conf`；官方脚本主要修改 `/boot/armbianEnv.txt`。应修改实际生效的引导配置并验证设备节点，不能以配置文件已写入作为启用成功的依据。

## 三、建议实施顺序

1. 保留当前 XL330 检查点；建立 HD-1910 平地及齿隙任务，完成短训练和配置验证。
2. 在 Radxa 上读通 15 颗舵机与直连 IMU，记录零位、方向、模式、增益、供电和延迟；测量整机质量及重心。
3. 用这些参数调整仿真，训练/微调 HD-1910 两版，并在普通/齿隙环境中交叉评估。
4. 核对 ONNX 观测/动作契约和 ARM64 推理，再进行支撑状态下的小范围动作与站立测试，之后测试低速平地行走。

本评估确定了源码缺口和适配方向；真实步态质量仍须以 HD-1910 仿真评估及上述机器的实测结果判断。
