## 核查内容

### 2. 协议与字节内容

对照仓库内的飞特 [SCS 协议手册](../../microduck-replica/docs/飞特资料/SCS通信协议-v1.0-2026-06-09.md)，第 4.1、4.2 节：

| 指令 | ID1 的完整十六进制报文 |
|---|---|
| PING | `FF FF 01 02 01 FB` |
| 读取当前位置的两个字节 | `FF FF 01 04 02 38 02 BE` |

部署驱动的输出与样例一致。对用户 ID1–14 的 PING、2 字节位置读取、15 字节反馈读取、身份读取共 56 组报文，
还与 [复刻驱动](../../microduck-replica/tools/servo-web/feetech.py) 逐字节对照，全部相同。

HD-1910 使用的 FT-SCS 报文与原版 Dynamixel 的驱动路径没有混用。

### 3. 串口设置与读写流程

- PySerial 3.5 实际设置为 1 Mbps、8 数据位、无校验、1 停止位。
- 接收使能 `CREAD` 打开；软件和硬件流控关闭；关闭终端回显和按行读取。
- 清接收缓冲发生在发送请求之前，没有在发送后立即清除回复。
- 单个请求整体写入；没有把二进制报文转成十六进制字符串再发送。
- 收包支持分段/逐字节到达，并验证 ID、长度、状态和校验和。
- 空应答会超时；损坏的校验和不会当作成功。

复刻 Rust 驱动发送后调用 `flush()`，当前 Python 驱动没有强制 `tcdrain()`。
这是一处实现差异，但不能认定是根因：此前 Radxa 原始报文测试已交替执行过 `flush()`，仍然没有 RX 字节。
不据此给控制循环加入可能阻塞的无截止时间操作。

### 4. 超时和诊断输出的边界

默认串口超时 15 ms；此前真实诊断已临时延长到 80、100、200 ms。
曾收到的有效 PING 只需约 2–3 ms，而其余请求长时间无字节。因此不能把全局超时增加视为已修复。
14 颗同步读取在真实负载下能否满足控制周期，仍需后续上电测量。

`scan` 会跳过单个 ID 的超时，所以 `found_ids=[]`、`errors=[]`、退出码 0 可以同时出现。
`errors=[]` 只表示没有记录到非超时异常，不能理解成通信正常。这是诊断输出的局限，不会造成接收不到字节。
