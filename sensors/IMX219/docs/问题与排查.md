# IMX219 实测问题与排查

更新：2026-11-05。完整部署命令见[部署说明](../README.md)，资料及固定版本见[资料来源](资料来源.md)。本文区分已实测的现象、已确认原因和仍待确认的画质问题。

## 1. 已经验证到哪一步

实测平台为 Radxa ZERO 3W / RK3566、aarch64、Debian Trixie 用户空间、`6.1.115-vendor-rk35xx` 内核、IMX219 CSI 模组。已完成摄像头识别、取流、ISP 安装、自动曝光、SSH 传回 NV12 与 PNG、文件 SHA256 核对。此次整理没有对另一台机器人进行实物验收。

| 项目 | 结果与边界 |
|---|---|
| 传感器识别 | I²C 地址 `0x10`，芯片 ID `0x0219`；测试机器实体名为 `m00_b_imx219 2-0010` |
| 图像链路 | `rkisp_mainpath` 可稳定抓帧；安装后传感器模式 1920×1080，默认输出 640×360 |
| ISP | `rkaiq_3A` 服务运行；测试抓帧后仍运行，记录的重启计数为 0 |
| 自动曝光 | 一次普通场景测试收敛：曝光 1760 行、增益控制 1130、全图 Y 均值约 98.77、高光剪切 0% |
| 白平衡、清晰度 | **尚未完成最终验收**。先前画面存在近距离、手遮挡、白纸受强直射光等条件，不能据此断言颜色或镜头有问题 |
| 最后保留的照片 | 白纸可辨，约 5.55% 高光剪切，`ae_converged=false`、`iteration_limit`；用户要求保留照片并暂停进一步拍摄 |

去标识的验证摘要在 [evidence/verification.json](../evidence/verification.json)。原始日志保留在本地 `archive/raw-reports/`，照片与原始 NV12 在 `archive/captures/`；这些资料不随公共 Git 仓库及默认部署包发布。需要复核完整现场时，另行传送对应原始目录。

## 2. 先保留日志，再按现象定位

在 Radxa 的 `sensors/IMX219` 目录执行：

```bash
mkdir -p diagnostics
python3 scripts/doctor.py --output diagnostics/doctor.json
sudo journalctl -k -b --no-pager > diagnostics/kernel.log
sudo journalctl -u rkaiq_3A -b --no-pager > diagnostics/rkaiq.log
systemctl status rkaiq_3A --no-pager
v4l2-ctl --list-devices
```

诊断文件生成成功不等于相机通过。结合报告中的命令返回码、设备节点、服务主进程与下面的症状判断。每次抓帧另保存 `capture.json`、`capture.log`、`ssh.log`、`transfer.log`；失败末尾的原始错误优先看 `capture.log`。分享日志前检查其中的主机信息和路径。

| 现象 | 先看什么 | 已知处理方向 |
|---|---|---|
| 没有 IMX219 实体或没有主采集节点 | 内核日志、设备树 overlay、排线 | 第 3 节 |
| `Input/output error`、`probe ... error -5` | 同次启动内核日志，是否绑定 `imx219` | 第 3 节；不能仅凭错误码定为欠压 |
| 文件有数据但很暗 | ISP 是否运行、`ae_history`、开流后控制是否应用 | 第 4–6 节 |
| 有图但偏绿 | IQ 文件、ISP 日志、照明与模组滤光片 | 第 7 节 |
| 服务显示 active 但拍摄无效果 | 真实 MainPID、日志、取流与服务启动先后 | 第 8 节 |
| `CIF_ISP_PIC_SIZE_ERROR` | 传感器模式是否在启动 ISP 后被改变 | 第 8 节 |
| `Permission denied`、设备忙 | `video` 组、输出目录归属、占用进程 | 第 9 节 |
| PNG 看着比原始数据更暗 | NV12 色彩范围、转换命令 | 第 10 节 |

## 3. 启动、排线与 I/O 错误

**实际遇到：**早期有成功抓到暗图、随后开流 `EIO` 的情况；另一次启动日志出现 `Reading register 100 from 10 failed`、`probe of 2-0010 failed with error -5`、`update sensor failed`。后续重新启动后的测试能够识别与取流。

这些记录确认当时存在传感器访问/链路初始化失败，**尚不能区分排线接触、供电、复位时序或其他硬件因素**。没有测量摄像头电源轨，也不能用机器人电池总电压推导摄像头供电是否合格。

处理顺序：

1. 确认机型与内核符合部署说明，启用 `radxa-zero3-rpi-camera-v2.dtbo` 后确实重启。
2. 确认主板 CSI 22P/0.5mm 与模组端接口、触点朝向、锁扣均匹配。
3. 若日志为传感器读寄存器失败，先完全断电（包括电池和 USB），再检查两端排线；复位上电后重新保留内核日志。
4. 若仍失败，使用已知正常的排线/模组做替换对比，必要时测量对应电源轨。不要边通电边插拔排线。

早期曾尝试驱动解绑/重绑，未由此解决问题；它不是本部署包的恢复步骤，也不做自动 I²C 扫描或强制寄存器写入。

原始依据：`archive/raw-reports/20261104_radxa_camera_live/`、`archive/raw-reports/20261105_radxa_camera_retest/after_restart.log`、`archive/raw-reports/20261105_radxa_camera_retry2/`。

## 4. 已确认的暗图原因：开流覆盖曝光，缓存读数会误导

在 3280×2464 模式，直接读取曝光寄存器 `0x015A/0x015B` 得到：

| 时刻 | V4L2 缓存显示 | 实际曝光寄存器 |
|---|---:|---:|
| 开流前设置曝光 | 2460 行 | 2460 行 |
| 开流后、重新写入前 | 2460 行 | **500 行** |
| 开流后强制重新写入 | 2460 行 | 2460 行 |
| 测试结束恢复 | 1575 行 | 1575 行 |

对应驱动的模式表在启动时写入 500 行，随后没有按期望重新应用该控制。`v4l2-ctl --get-ctrl` 在这里读的是控制缓存，不能证明传感器寄存器实际值。重复写相同缓存值还可能被 V4L2 跳过。

包内抓帧脚本会先开流，等待新帧，再写一个合法相邻值并写目标值，保证控制实际下发；曝光调整后等待后续帧再测光。结束时停止取流并恢复原缓存控制值。**不要改回“开流前设曝光，随即只抓一帧”的流程。**

同一连续流中，500 行/2 倍增益时 Y 均值约 24.40，2460 行/2 倍约 46.90，2460 行/11 倍约 143.89，支持曝光和增益控制在开流后有效。该组是旧全幅模式诊断值，不是当前 1080p 的推荐参数。

原始依据：`archive/raw-reports/20261105_camera_brightness_audit/exposure_register_readback.log`、`register_snapshots.json`、`stream_exposure_probe.log`。

## 5. 曝光单位、帧率与增益控制

`exposure` 的单位是**传感器行数**，不是毫秒。按已核对模式寄存器和 Sony 数据手册计算，一行约 18.90µs：500 行约 9.45ms，1575 行约 29.78ms，2460 行约 46.51ms。换模式或时钟后必须重新核对，不能将这些时间套用所有 IMX219 驱动。

| 模式 | 模式表帧长 | 本包曝光上限 | 用途 |
|---|---:|---:|---|
| 1920×1080 | 1766 行 | 1760 行 | 当前已部署模式，约 30fps |
| 3280×2464 | 2500 行 | 2496 行 | 历史诊断模式，约 21.16fps |

在 1080p 中照搬 2460 行会超出该模式帧长。当前脚本按模式限幅，增益最多 2048（8 倍），不会沿用旧诊断的 11 倍高增益。

本次 vendor 驱动中 `analogue_gain` 控制按 256 表示 1 倍、512 表示 2 倍；驱动的 `gain` 和 `analogue_gain` 会写同一套硬件增益寄存器，**不能把它们当两个独立乘数同时调节**。本包只写 `exposure` 与 `analogue_gain`。这些控制名和缩放是此驱动的实现，不是所有 Linux 相机的通用约定。

## 6. 必须明确由谁控制自动曝光

当前路径是：

```text
IMX219 RAW → RKISP + rkaiq（白平衡/颜色处理）→ NV12
                    ↑
抓帧脚本读取亮度，调整 IMX219 曝光与增益
```

IQ 中的引擎 AE 关闭，由 `capture_frame.sh` 在本次抓帧期间控制曝光。这样不会与引擎或 `mediad` 同时写曝光。安装器没有手动重调 AWB、CCM、Gamma 的数值。

旧上游安装路线原本依赖 `mediad` 接管曝光。如果只装 ISP 并关掉引擎 AE，却没有运行相应曝光循环，相机仍可能一直很暗。混合文档中的旧 `photo/record` 入口不具备本次自动曝光循环；历史脚本留作参考，不是本包推荐入口。

脚本发现 `mediad` 正在运行，或检测到引擎 AE 仍启用时会拒绝竞争。确认改用单帧方案后，再由使用者停止当前摄像头使用程序。长期视频需要持续曝光控制，不能从一张 PNG 成功推断连续视频也已完成调试。

## 7. 偏绿、白纸和官方参数

IMX219 输出 Bayer 原始数据，最终颜色还取决于 ISP 白平衡、颜色矩阵、Gamma、镜头及红外滤光片。传感器数据手册给出电气/寄存器/光谱等规格，不保证任意模组在任意软件上直接得到准确颜色。

本包使用 **Radxa 的 `imx219_rpi-camera-v2_default.json` 官方 IQ**，保留颜色参数，只做两处枚举字符串兼容及 AE 归属调整，详见[资料来源](资料来源.md)。Raspberry Pi 自己也有 IMX219 调校文件，但 ISP 和配置格式不同，不能直接替换 Rockchip JSON。

普通白纸用于快速观察中性区域是否明显偏色、是否过曝、文字是否清楚，**不是完整相机标定**，也不是每次拍照必须摆白纸。验收时让相机朝向约 0.5–1m 外场景，白纸与其他物体同时入镜，室内灯均匀照明，避免手遮挡和手电直射亮斑。要做准确颜色标定，需适合的色卡、已知光源和正式 ISP 调校流程。

目前尚未核实采购模组的具体镜头/红外滤光片是否完全等同 Raspberry Pi Camera V2。因此，“官方 IQ 已加载”可以确认；“该模组在所有光源下色彩已校准”不能确认。

`success=true` 表示图像保存成功；`ae_converged=true` 才表示达到脚本本次测光目标。后者也不等于白平衡与清晰度通过。`control_limit` 表示达到控制上限，`iteration_limit` 表示有限轮调整结束；先看照片、测光历史和高光剪切，不要无条件把增益继续加大。

## 8. ISP 安装与服务兼容问题

| 问题 | 依据或现象 | 本包处理 |
|---|---|---|
| 缺少 ISP 服务及 IQ | 初期检查未安装完整引擎/IQ | 固定下载并校验已测试的两个 Radxa 包 |
| 私有 ioctl 结构大小不一致 | 上游 shim 明确记录旧引擎与 vendor 内核 5203/5207 字节差异，可导致 IQ 路径为空、崩溃；本次沿用此兼容修复 | 现场编译 `rkaiq-modinfo-shim.c`，仅给 `rkaiq_3A` 设置 `LD_PRELOAD` |
| 隐含 `libdrm2` 依赖 | 引擎包依赖字段未完整列出运行库 | 安装器补齐并检查动态库缺失 |
| IQ 枚举不被旧引擎识别 | 固定引擎/IQ 组合所需格式适配 | 替换两处枚举名称，保留颜色数值 |
| 数据手册下载 HTTP 403 | 整理时从空目录下载，Arducam CDN 拒绝 Python 默认 User-Agent | 下载器使用浏览器兼容 User-Agent，并继续严格核对 SHA256；交付包已缓存 PDF |
| 服务 Type=forking 与包装进程 | 旧启动脚本经 shell/logger 包装，不利于核实引擎本体状态 | drop-in 改为 `Type=simple`，直接运行引擎，日志入 journal |
| 原有 systemd drop-in 覆盖新配置 | 整理时审查发现：已有上游 `robot.conf` 可在 `90-microduck-capture.conf` 之后生效；这不是本次现场故障 | 安装前检查并列出其他 drop-in，拒绝覆盖；完成配置后核验实际执行命令与 `LD_PRELOAD` |
| 模式与 ISP 预期不一致 | 取流模式与 ISP 初始化参数不一致可能报尺寸错误 | 服务启动前固定传感器 1920×1080；先启动引擎，再开流 |
| 拍摄中重启引擎 | 可能错过 stream-start 事件 | 停止采集后才维护服务；脚本检查占用 |
| `/etc/iqfiles` 指向包内原件 | IQ 包安装脚本建立符号链接 | 安装器原子替换为独立配置文件，避免顺着链接修改 `/usr/share` 原件 |

核对命令：

```bash
systemctl show rkaiq_3A -p MainPID -p Type -p NRestarts -p ExecMainStatus
systemctl cat rkaiq_3A.service
sudo journalctl -u rkaiq_3A -n 100 --no-pager
ldd /usr/bin/rkaiq_3A_server
sha256sum /etc/iqfiles/imx219_rpi-camera-v2_default.json
```

在已测组合，修改后的 IQ SHA256 应为 `2cf410aca8051810369eac2c52717be2889c4a7329fc229ea5e36c2cbf77f53b`。核对引擎日志中的实际加载情况；仅文件存在还不够。首次安装时看到 `Unit rkaiq_3A.service not loaded` 可能只是停止尚不存在的旧服务，需看安装最终返回码和后续服务状态。

原始依据：`archive/raw-reports/20261105_camera_isp_setup/`；ioctl 兼容机理来源为随包上游 shim 注释，不把它记为此次现场未装 shim 的失败对照试验。

安装报 `Existing rkaiq/system service drop-ins` 时，先确认继续使用原 `mediad` 媒体栈还是迁移至本包单帧方案，
备份并逐项核对列出的覆盖文件后再安装；不要为消除报错直接删除所有 systemd drop-in。

## 9. 权限、占用与启动配置

- 相机节点由 `video` 组访问；新增组成员后必须退出并重新 SSH 登录。不要用 `chmod 777` 长期开放设备或用户目录。
- 早期曾由 root 建立媒体日志目录，导致普通用户无法写入；本包优先使用用户目录和临时目录。若自建目录归属错误，确认目标后修正该目录归属，不要递归更改整个系统或机器人的部署目录。
- 用 `v4l2-ctl --list-devices` 找 `rkisp_mainpath`，设备编号可能变化。`fuser -v /dev/video0` 仅是主采集节点恰为 video0 时的示例；停止确认占用它的采集程序，再抓帧。ISP 正常占用 stats/params 节点并不等于主采集节点被抢占。
- 某些新版本 `v4l2-ctl` 对旧内核输出 `VIDIOC_SUBDEV_S_CLIENT_CAP ... Inappropriate ioctl for device`，随后仍能打印有效格式。这个警告本身不能证明传感器坏；结合返回信息及 `media-ctl -p`。
- 本包使用已核对的 extlinux 启动配置。早期测试板的 `armbianEnv.txt` 存在 NUL 损坏内容，但活动启动路径是 extlinux；当时保持它不变。不要把这项个例当作所有板都有的问题，也不要为相机覆盖整份启动配置。
- 摄像头使用 I²C2，已有 J5/IMU、UART、音频 overlay 需要保留；不需要为了安装摄像头运行整个音频/DKMS 安装器。启动配置预览不通过时，先确认差异原因，不跳过检查强行套用。

## 10. 原始数据、转换和画质边界

`frame.nv12` 是 ISP 输出的未压缩 YUV 帧，**不是传感器 Bayer RAW**。640×360 NV12 应为 `640 × 360 × 3 / 2 = 345600` 字节；传回后脚本核对 SHA256，再生成 PNG。

测试设备协商为 Full Range，转换必须按元数据解释色彩范围，不能默认按 Limited Range 解码。范围误用会改变暗部和对比度，但不能解释此前曝光寄存器被重置这一主因。脚本不对 PNG 额外加绿色抑制或伪造白平衡。

默认 640×360 是便于远程检查的输出，不是 800 万像素画质验收。需要更大分辨率、连续录像、画面旋转或 WebRTC 时，应在本链路通过后分别实现并验证；不要随意改变传感器模式却让 ISP 继续按旧模式运行。
